# プロジェクトおよびサンドボックス払い出しガイド

本ドキュメントは、Google Cloud プロジェクトの新規作成、サンドボックスの払い出し、およびデプロイの手順について記述したものです。

---

## 1. プロジェクトの申請と作成

### 1.1 通常プロジェクト (App Projects)
1.  `governance/admin/factory/inventory.json` を更新します。
2.  **直接のプッシュは禁止**されているため、必ず Pull Request (PR) を作成してください。
3.  PR作成後、自動で実行される「AI検閲 (`AI-Verifier`)」および「Checkov (セキュリティ解析)」を通過（Status Check が Success になること）がマージの必須条件です。
    - **AI検閲の合否**: `RESULT: PASS` の明示一致で合格、それ以外（FAIL・想定外応答）は Failure/error でブロックされます（Fail-Closed）。指摘は PR コメントに出ます。
    - **Draft PR の扱い**: Draft の間は FAIL でもブロックせず Status Check は **Pending（非ブロック）** になります（Draft はそもそもマージ不可）。Ready for Review にした時点で再検閲が走り、Success になるまでマージできません（判例 DX-001）。
    - **Vertex 障害時**: リトライ＋モデル/リージョンのフォールバックで自動回復を試みます。長時間障害でどうしてもマージが必要な場合のみ、管理者バイパス（break-glass）を PR コメントへの記録付きで行います（判例 OPS-008・詳細は `docs/SPEC_AI_VERIFIER_CLOUDBUILD.md`）。
4.  （※現在の1名体制の運用ルール上、他者のレビューは必須としておらず、チェックを通過すれば**自己マージが可能**です）
5.  マージされると、GitHub Actions が発火し自動的にプロジェクトが作成されます。

### 1.2 サンドボックス (Sandboxes)
1.  GitHub Actions の **「GCP: Create Sandbox」** ワークフローを実行します。
2.  `sandbox_id` と `github_repo` を入力して実行すると、自動的に `inventory.json` が更新され、プロジェクトが払い出されます。

## 2. セットアップ手順 (重要)

プロジェクト作成が完了すると、基盤ボットが**自動的にあなたのリポジトリの初期設定を行います。**

### 2.0 セキュリティ・ガードレール (Checkov) について
本基盤から払い出されたアプリ・サンドボックスのリポジトリは、**「Security: Checkov (Project Strict)」** というセキュリティ監査ワークフローの監視対象になります。
- `infra/main.tf` などに変更を加え、公開設定などの意図しないセキュリティホール（脆弱性）が混入した場合、GitHub Actionsのチェックで自動的にブロック（FAIL）されます。
- これは基盤管理者が全プロジェクトに適用している安全装置です。エラーになった際はログの指摘事項（例: `Ensure public access prevention is enforced`）を修正して再コミットしてください。

### 2.1 GitHub Variables の自動同期
1.  基盤側の処理が完了すると、あなたのアプリリポジトリの **「Settings」>「Secrets and variables」>「Actions」** に、デプロイに必要な ID 群（`ID_STG`, `ID_PRD`, `APP_NAME` 等）が自動的に書き込まれます。
2.  開発者は Slack 通知、または GitHub の設定画面を確認し、設定が届いていることを確認するだけです。**YAML への手動コピペは不要です。**

### 2.2 本番環境 (prd) の承認ルール設定
本番環境への誤デプロイを防ぐため、GitHub リポジトリの Environment 保護設定を行います（※`scripts/setup_required_checks.sh` によって自動構成されます）。

- **1名体制・少人数体制の場合（現状の仕様）**
  - デプロイ時の「自己承認」が許可されています（`prevent_self_review: false`）。これにより、他者の承認を待たずにデプロイを進めることができます。
- **複数人体制へ移行した場合**
  - スクリプトの設定を変更（`prevent_self_review: true` 等）することで、本番デプロイ時に「第三者の承認ボタン」を必須化し、厳格な職務分掌へ即座に引き上げることが可能です。

## 3. デプロイの実行

本基盤の雛形ワークフローは、GitHub Variables を自動的に読み込み、**「インフラ（Terraform）」と「アプリプログラム（gcloud等）」** を適切な順序でデプロイします。

### 3.1 通常デプロイ (`app_deploy.yml`)
本基盤の雛形は、安全かつ効率的な **「多段階スマート・パイプライン」** を採用しています。

#### デプロイの流れ
1.  **DEV環境 (自動)**: `main` ブランチへのプッシュで自動実行されます。
    - ※ Variables に `ID_DEV` が設定されていない場合は、自動的に **Skipped (灰色 ⚪️)** となり、次のステップへ進みます。
2.  **STG環境 (自動)**: DEVデプロイが成功（またはスキップ）した後に自動実行されます。
3.  **PRD環境 (手動)**: 本番事故防止のため、自動実行はされません。GitHub Actions の画面から手動で実行（workflow_dispatch）する必要があります。

#### 特徴
- **正直なステータス**: デプロイが実行されたのか、環境未設定で飛ばされたのかが GitHub 上で明確に区別されます。
- **連鎖の停止**: 前の環境でエラーが発生した場合、後続の環境へのデプロイは安全のために自動的にキャンセルされます。

### 3.2 サンドボックスデプロイ (`sandbox-deploy.yml`)
- `sandbox/**` ブランチへのプッシュ、または手動実行。
- 自分のサンドボックスプロジェクト内だけで、自由に実験が可能です。

---

## 4. ライフサイクルと自動削除

- **サンドボックスの期限**: 作成時に指定した期限（デフォルト 7日）が過ぎると自動削除されます。
- **削除フロー**: ボットが `inventory.json` から定義を削除し、Terraform が物理削除を行います。
- **ゾンビ防止**: 台帳（Git）と実体（GCP）が常に同期されるため、削除後の不要な課金は発生しません。
